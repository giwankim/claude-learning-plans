# A From-Fundamentals Learning Plan for JVM Concurrency (2026 Edition)

## TL;DR
- Start with the classical core (Java Memory Model, threads, `java.util.concurrent`, locks, atomics, lock-free structures) using *Java Concurrency in Practice*, Aleksey Shipilëv's JMM writings, and the Rice Coursera specialization. Then layer on the modern JVM (virtual threads/Loom, structured concurrency, scoped values) and Kotlin coroutines. The order matters because coroutines and virtual threads only become fully intelligible once you own happens-before, safe publication, and executor/blocking semantics.
- Verified 2026 state: Java 25 is the current LTS. Scoped values are final (JEP 506) and virtual-thread pinning on `synchronized` is essentially fixed (JEP 491, delivered in JDK 24), but structured concurrency is still preview (JEP 505 in JDK 25, JEP 525 in JDK 26, JEP 533 targeted for JDK 27), so treat `StructuredTaskScope` as something to learn now and ship carefully. kotlinx.coroutines is at 1.11.x (Kotlin 2.2.x). Spring Boot has enabled virtual threads with one property (`spring.threads.virtual.enabled=true`) since 3.2.
- The roadmap runs about 12 to 18 months. Phase 1 (months 1-3) is foundations. Phase 2 (months 3-9) covers `j.u.c` mastery, lock-free structures, coroutines internals, Loom internals, and testing with Lincheck/jcstress/JMH. Phase 3 (months 9-18+) is research-grade theory (linearizability, memory models), production tuning tied to your Kafka/Aurora/EKS stack, and a mini structured-concurrency library. Every phase has hands-on projects.

## Key Findings

1. The classical core is the substrate, not legacy material. Virtual threads are still threads, coroutine dispatchers still wrap executors, and `ConcurrentHashMap`, `CompletableFuture`, and the JMM's happens-before are as load-bearing in 2026 as they were in 2006. Your pure-math background helps here: the field has a rigorous formal core (linearizability, memory-consistency models, wait-free hierarchies) that most engineers skip, and it pays off directly when reasoning about lock-free code and weak memory behavior.

2. What changed in 2026 is the set of tradeoffs, not the fundamentals. JEP 491 (JDK 24) removed the biggest virtual-thread footgun, pinning inside `synchronized`, which had caused a well-documented Netflix production incident on Java 21. The fix requires no code changes; per JEP 491, "Existing applications with synchronized blocks automatically benefit from the fix when they upgrade to Java 24 (or Java 25 LTS, which inherits the fix)." That changes the advice ("you can use `synchronized` again") without changing what you need to understand. You still have to know why pinning happened in order to reason about the remaining native and JNI cases.

3. Virtual threads versus coroutines is still a live decision, and Korean engineering blogs have unusually strong primary material on it. Woowahan and Kakao Pay both published head-to-head benchmarks and decision frameworks in Korean, directly usable given that you work bilingually.

4. Your own stack is the lab equipment. Kafka consumer threading, Spring `@KafkaListener` concurrency, HikariCP pool sizing (Little's Law plus the Universal Scalability Law), and Spring Boot's virtual-thread switch are all places where abstract concurrency becomes concrete.

## Details

### Verified current-state facts (as of July 2026)
- Java LTS: Java 25 is the current LTS. Scoped values are finalized as a standard API in JDK 25 (JEP 506), with one behavior change against the preview: `orElse` no longer accepts null. Structured concurrency remains preview. JEP 505 (JDK 25, 5th preview) was a major API rework that decoupled `StructuredTaskScope` from the join policy via a `Joiner` and moved to static `open()` factory methods, "composition over inheritance". JEP 525 (JDK 26, 6th preview) makes `join()` return the result list directly. JEP 533 (targeted JDK 27, 7th preview) plans to switch standard joiners to throw `ExecutionException` instead of `FailedException`.
- Pinning: JEP 491 "Synchronize Virtual Threads without Pinning" was delivered in JDK 24. Monitor ownership is now tracked per virtual thread rather than per carrier; the `-Djdk.tracePinnedThreads` system property was removed; use the `jdk.VirtualThreadPinned` JFR event (enabled by default, ~20 ms threshold). Remaining pinning cases: native/JNI calls and Foreign Function & Memory API callbacks, plus rare class-initialization edge cases.
- kotlinx.coroutines: 1.11.x, the companion release line for Kotlin 2.2.x.
- Spring Boot: `spring.threads.virtual.enabled=true` (available since 3.2) makes Tomcat/Jetty use a virtual-thread-per-request executor and auto-configures `SimpleAsyncTaskExecutor` (with `setVirtualThreads(true)`) as the default `@Async` executor. It also affects `@Scheduled` tasks, Kafka/RabbitMQ listeners, Spring Data Redis, and blocking WebFlux calls. Watch two pitfalls: ThreadLocal/MDC memory and inheritance behavior (always `MDC.clear()` in a `finally`), and connection-pool sizing (below).

### Phase 1: foundations (months 1-3, ~6-8 hrs/week)
**Topics**: thread lifecycle and states; `Runnable`/`Callable`; `synchronized`, monitors, `wait`/`notify`; the Java Memory Model (happens-before, `volatile`, final-field semantics, safe publication, data races, "out of thin air" values); the fundamentals of `java.util.concurrent`: `ExecutorService`, `Future`, thread pools.

**Resources**:
- Book (spine): *Java Concurrency in Practice*, Brian Goetz et al. (2006). Still the single best treatment of the JMM in practice and of safe publication. One caveat: it predates `CompletableFuture`, Loom, and modern collectors, so pair every chapter with current JEPs and JDK docs.
- Book (reference): *Effective Java* (3rd ed.), Bloch, specifically the concurrency chapter.
- Primary sources: JLS Chapter 17 (Threads and Locks / the JMM); Aleksey Shipilëv's "Java Memory Model Pragmatics" (shipilev.net/blog/2014/jmm-pragmatics/), "Safe Publication and Safe Initialization" (2014), and "Close Encounters of the JMM Kind" (2016); Doug Lea's "JSR-133 Cookbook for Compiler Writers" (gee.cs.oswego.edu/dl/jmm/cookbook.html).
- Course: Rice University "Parallel, Concurrent, and Distributed Programming in Java" specialization on Coursera (Prof. Vivek Sarkar). The Concurrency course explicitly covers threads, locks, atomics, concurrent collections, and their theoretical foundations (linearizability, progress guarantees, memory models).
- Korean: Devsisters "바삭한 신입들의 동시성 이야기 - Kotlin 편" (tech.devsisters.com/posts/crunchy-concurrency-kotlin/) for the CPS/continuation intuition in your working language.

**Projects**:
- P1a: Build a fixed-size thread pool from scratch (blocking queue + worker threads + graceful shutdown), then compare against `ThreadPoolExecutor`.
- P1b: Write JMM "litmus tests" by hand (store buffering; safe vs. unsafe publication of a config object) and predict legal outcomes *before* running them.
- P1c: Implement a thread-safe bounded cache with correct safe publication; deliberately break it (drop `volatile`/`final`) and observe.

### Phase 2: deepening and the modern JVM (months 3-9, ~6-10 hrs/week)
**Topics**: full `java.util.concurrent`, meaning `CompletableFuture` composition, `CountDownLatch`, `Semaphore`, `CyclicBarrier`, `Phaser`, `ReentrantLock`/`ReadWriteLock`/`StampedLock`, `ConcurrentHashMap`, and the `BlockingQueue` family; atomics and CAS, the ABA problem, `LongAdder`; `ForkJoinPool` and work-stealing; lock-free/wait-free structures (Treiber stack, Michael-Scott queue); virtual threads and Loom internals (continuations, carrier mounting/unmounting, M:N scheduling, pinning, monitoring); structured concurrency (`StructuredTaskScope` + `Joiner`); scoped values vs. `ThreadLocal`; Kotlin coroutines internals (suspension, continuation-passing style, dispatchers, `Job`/structured concurrency, channels, flows, `SharedFlow`/`StateFlow`, exception handling); a brief reactive context (Project Reactor/RxJava and why virtual threads reduce the need for them); testing (jcstress, Lincheck, JMH).

**Resources**:
- Books: *The Art of Multiprocessor Programming*, 2nd ed. (Herlihy, Shavit, Luchangco, Spear, Morgan Kaufmann, Sept 2020) is the definitive lock-free/synchronization text, updated with new algorithms and exercises. *Kotlin Coroutines: Deep Dive* (Marcin Moskała, Kt. Academy) is the best coroutines book; the Leanpub edition is kept current, last updated 2026-06-12, and a third print edition has shipped. It covers builders, context, `Job`s, cancellation, dispatchers, channels, flows, testing, and best practices, including "coroutines under the hood."
- Primary sources / JEPs: JEP 444 (virtual threads, final in 21), JEP 491 (pinning fix, JDK 24), JEP 505/525 (structured concurrency previews), JEP 506 (scoped values, final), plus the lineage JEPs 453/462/480 (structured concurrency) and 429/446/464/487 (scoped values); Ron Pressler's "State of Loom" parts 1 & 2 (cr.openjdk.org/~rpressler/loom/) and his QCon/InfoQ talks on continuations; Oracle's structured concurrency core-libraries guide (docs.oracle.com/en/java/javase/25/core/structured-concurrency.html); Kotlin official coroutines docs (kotlinlang.org/docs/coroutines-guide.html).
- Kotlin design source: Roman Elizarov's "Structured concurrency" (Medium, 2018) and "Structured Concurrency Anniversary" (2019); his KotlinConf/Hydra talks (speakerdeck.com/elizarov/structured-concurrency); "Deadlocks in non-hierarchical CSP" for channel pitfalls.
- Testing: Lincheck (JetBrains) does declarative concurrency testing with both stress and bounded model-checking modes; the current artifact is `org.jetbrains.lincheck:lincheck:3.6`. - Engineering blogs (international): Netflix Technology Blog, "Java 21 Virtual Threads - Dude, Where's My Lock?" (July 2024). ### Phase 3: mastery, theory, and production (months 9-18+, ~4-8 hrs/week)
**Topics**: formal foundations, meaning Lamport's "Time, Clocks, and the Ordering of Events in a Distributed System" (1978, happens-before), Herlihy & Wing's "Linearizability: A Correctness Condition for Concurrent Objects" (ACM TOPLAS, 1990), Herlihy's "Wait-Free Synchronization" (1991, the consensus hierarchy), and memory-consistency models (sequential consistency, TSO); production observability (thread dumps via `jcmd`, including the JSON virtual-thread dumps that show `StructuredTaskScope` hierarchies, JFR, async-profiler); and applying all of it to your Kafka/Aurora/EKS stack.

**Resources**:
- Papers: the three foundational papers above (all directly relevant to lock-free reasoning and linearization points); the Lincheck CAV'23 paper; optionally "LitmusKt: Concurrency Stress Testing for Kotlin" (arXiv:2501.07472) for memory-model testing on Kotlin.
- Books: revisit *Art of Multiprocessor Programming* chapters on consensus, universality, and transactional memory now that you have the practice under your belt.
- Stack-specific: the HikariCP "About Pool Sizing" wiki (Brett Wooldridge) gives the heuristic verbatim: "for optimal throughput the number of active connections should be somewhere near ((core_count * 2) + effective_spindle_count). Core count should not include HT threads... Effective spindle count is zero if the active data set is fully cached." The same page documents an Oracle Real-World Performance demo where "reducing the connection pool size alone, in the absence of any other change, decreased the response times of the application from ~100ms to ~2ms," an improvement of over 50x, and it recommends "a small pool of a few dozen connections at most." Pair that with Vlad Mihalcea's "The best way to determine the optimal connection pool size" (Universal Scalability Law + FlexyPool) and apply Little's Law (L = λW) as directional guidance for average concurrency. Then read the Spring Kafka `@KafkaListener` docs and Piotr Minkowski's "Concurrency with Kafka and Spring Boot". The rule to remember: `concurrency` ≤ partition count (extra threads sit idle), thread-per-partition preserves per-partition ordering, and offloading to an app-level `ExecutorService` regains parallelism but loses single-partition ordering.
- Observability: use `jcmd <pid> Thread.dump_to_file -format=json` to see virtual-thread and scope hierarchies; async-profiler for wall-clock/CPU flame graphs; JFR `jdk.VirtualThreadPinned` events to catch remaining native-pinning.

- P3a: Build a mini structured-concurrency library in Kotlin (or Java) from primitives. Implement scopes, cancellation propagation, and error aggregation, then compare your API and semantics to `StructuredTaskScope` and `coroutineScope`.
- P3b: Kafka consumer with manual partition assignment and a custom threading model; measure ordering guarantees and rebalance behavior; then contrast with `ConcurrentKafkaListenerContainerFactory` concurrency settings.
- P3c: Production tuning study on an EKS service. ### Honest tradeoffs and decision frameworks
- When not to use virtual threads: CPU-bound work (use platform threads, parallel streams, or ForkJoin); code with heavy native/JNI on the hot path (still pins post-JEP 491). And never pool virtual threads. They are cheap to create, so bound concurrency against a downstream dependency with a `Semaphore` rather than a fixed pool. Virtual threads improve throughput rather than latency.
- Coroutines vs. virtual threads: coroutines win for structured concurrency, fine-grained cancellation, flows and event streams, high-concurrency fan-out/merge, and pre-JDK-21 runtimes. They carry the "function color" (`suspend`) propagation cost and demand strict non-blocking discipline, since a stray blocking call can stall a dispatcher. Virtual threads win for thread-per-request blocking code, reuse of existing blocking libraries, and Java-ecosystem generality. The two are complementary: a coroutine dispatcher can run atop a virtual-thread executor, and the Woowahan and Kakao Pay posts frame them as coexisting rather than competing.
- Lock-free complexity cost: lock-free code is dramatically harder to get right (ABA, safe memory reclamation, subtle linearization points) and must be verified with Lincheck or jcstress. Prefer `j.u.c` structures unless profiling proves a specific bottleneck. This is where your formal background earns its keep, and it is also where confidence without model-checking is most dangerous.

## Recommendations
1. Months 1-3 (foundations): read *JCIP* cover to cover alongside Shipilëv's "JMM Pragmatics"; complete the Rice Concurrency course; ship P1a through P1c. Advance when you can explain happens-before from memory and justify every `volatile` and `final` in a safe-publication example without notes.
2. Months 3-9 (deepening): work through *Art of Multiprocessor Programming* (through lock-free structures) and *Kotlin Coroutines: Deep Dive* in parallel; make Lincheck and JMH standing habits; ship P2a through P2e. Advance when a Lincheck test of yours catches a real interleaving bug and your load test cleanly reproduces and then resolves the JDK 21→24 pinning story.
3. Months 9-18+ (mastery): read Lamport (1978) and Herlihy-Wing (1990); build the mini structured-concurrency library (P3a); run the Kafka and HikariCP production studies (P3b, P3c). Advance when you can derive a defensible connection-pool size from Little's Law plus core count, and defend a coroutines-versus-virtual-threads choice for a specific service with your own data.
4. Thresholds that change the plan: if your team standardizes on virtual threads across services, front-load Phase 2's Loom internals and observability (P2d, P3d) ahead of lock-free theory. If your team moves toward heavy reactive or streaming work, prioritize flows, channels, and Project Reactor. If you stay predominantly Kotlin and Spring MVC with blocking I/O, treat virtual threads (not WebFlux) as your default scaling lever and invest most in coroutines for the genuinely concurrent fan-out paths.

## Caveats
- Structured concurrency is still a preview feature through at least JDK 27. Its API changed materially between JDK 21 and 25 (the `Joiner` rework) and will change again in 27 (exception types). Learn the concept and prototype now, but gate production use behind `--enable-preview` awareness and expect churn.
- *Java Concurrency in Practice* (2006) is authoritative on fundamentals but silent on everything after Java 5 (`CompletableFuture`, Loom, modern GCs). Always cross-check API specifics against current JDK docs.
- Benchmark figures cited here are hardware- and workload-specific single-run results, not universal laws. Woowahan's "37% faster" was measured at 510 vusers on their specific I/O-bound test; various "~2x" Spring Boot virtual-thread numbers and the HikariCP "50x" figure come from particular demos. Treat all of them as directional and re-measure on your own EKS/Aurora setup.
- The Naver D2 URL was verified by strong cross-reference, but d2.naver.com blocks automated fetching, so confirm it loads in a browser. Likewise, a `tech.kakao.com/posts/608` virtual-thread post is cited by third parties but was not directly opened during research; verify before relying on it.
